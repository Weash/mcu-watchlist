# MCU watchlist

A private watchlist of every Marvel Cinematic Universe feature film, on a
Cloudflare Worker. SvelteKit + Tailwind + D1, gated by Cloudflare Access.

## Architecture

- **Auth** — Cloudflare Access (Google SSO) sits in front of the Worker; the
  Worker verifies the Access JWT itself rather than trusting it is behind the
  gate. Ticks are keyed on the JWT's `sub` claim. `/admin` is additionally gated
  on `OWNER_SUB`.
- **Data** — D1, via Drizzle. `films` is the catalogue, `watches` is one row per
  (user, film) seen. Nothing writes to `films` but you, through `/admin`.
- **Rendering** — SSR with form actions. The page arrives with your ticks,
  counts and progress bars already correct, so there is no loading state.
  `use:enhance` makes a tick feel instant; it falls back to a full form post
  with JavaScript disabled.

Three things are worth knowing before changing anything:

- **`upcoming` is not stored.** It is derived from `release_date > today`, so a
  film becomes tickable on its release day with no deploy and no UPDATE, and the
  "38 released films" count corrects itself.
- **`release_date` is the only field nothing else corrects.** There is no sync:
  when Marvel moves a film, you edit the date in `/admin` or the page is wrong.
  This is why Edit exists and why its tests are the ones to keep passing.
- **Saga is really a property of the phase.** Phases 1–3 are the Infinity Saga,
  4–6 the Multiverse Saga; none has ever spanned two. It is stored per film
  anyway — normalising it into a `phases` table would be a table, a migration
  and an admin surface for something that changes once every three years — but
  the Add form derives it from the chosen phase rather than asking twice, which
  is what stops `The Multiverse Saga ` from splitting the page into two
  identically titled sections.

**Phase colours live in the frontend**, not the database. They are design tokens
chosen to work against the paper background — you would change them by editing a
stylesheet, never by running an UPDATE. `MAX_COLOURED_PHASE` in
`src/lib/phases.ts` is how the admin form knows a phase has no colour yet.

## Local development

```bash
npm install
npm run fonts              # download the Latin-subset woff2 files (once)
cp .dev.vars.example .dev.vars
npm run db:migrate:local   # creates and seeds a local D1
npm run dev
```

Cloudflare Access is not in front of `vite dev`, so there is no JWT locally.
`hooks.server.ts` uses `DEV_USER_SUB` instead — gated on `dev`, a build-time
constant, so the branch is eliminated entirely from the production bundle. It is
deliberately **not** conditioned on a missing header, which would make any
Access misconfiguration an authentication bypass in production.

## Tests

```bash
npm test
```

Vitest over `node:sqlite` behind Drizzle's sqlite-proxy driver, applying the
real migration files with **foreign keys on**. Production is D1; both are
SQLite and Drizzle emits the same SQL against either, so the gap is smaller
than running the workers pool would cost.

The suite exists mostly for two things: the release-date edit path, which is
now the only thing keeping the page correct, and migration `0003`, which
rebuilds `films` while `watches.film_id` cascades off it.

## Deploying

```bash
npx wrangler d1 create mcu-watchlist    # put the id in wrangler.jsonc
npm run db:migrate                      # apply migrations remotely
npm run deploy
npx wrangler secret put OWNER_SUB       # your Google identity's `sub` claim
```

`ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are plain vars in `wrangler.jsonc` — fill
them in from your Access application's settings.

Access protects the whole hostname, and Cloudflare only emits
`Cf-Access-Jwt-Assertion` because an Access application exists — an unprotected
host sends no such header, whatever you read online.

## Migrations

```bash
npm run db:generate        # after changing src/lib/server/db/schema.ts
npm run db:migrate:local
```

Two traps, both of which have already bitten:

**Numbering.** `drizzle/0001_seed_films.sql` is a hand-written data migration
generated by `npm run seed:generate`, and drizzle-kit's journal has no entry for
it. The journal is now consistent (its last `idx` is 3, so the next generate
produces `0004`), but the underlying mismatch stands: if you ever renumber
something, check `drizzle/` for a filename collision afterwards. A test asserts
no two migrations share a prefix.

**What actually applies them.** `wrangler d1 migrations apply` runs the sorted
directory listing. Drizzle's `_journal.json` is bookkeeping for generating the
next migration and nothing else — reading it to decide what to run silently
skips the seed.

**Generated migrations are a draft, not an answer.** The `0003` drizzle-kit
produced was wrong in three ways, including guarding a table rebuild with
`PRAGMA foreign_keys=OFF`, which D1 does not honour — leaving `DROP TABLE films`
free to cascade every tick away. Read what it emits. The reasoning for the
hand-edits is in the migration's own header.

## Styling

Tailwind v4, configured entirely in `src/app.css`. The palette, the three font
families, and the type-scale additions live in `@theme`.

The six phase colours are in a separate `@theme static` block, and that matters:
they are applied by setting `color` inline on a phase container and letting
`border-current` / `bg-current` inherit it — the same `currentColor` mechanism
the original design used, where one value drives the checkbox border, its fill,
and the tag. Because that reference lives in a `style` attribute rather than a
utility class, Tailwind's tree-shaking cannot see it and drops the variables,
silently rendering four of the six phases black. `static` emits them all.

Adding a Phase 7 therefore means two edits: a `--color-phase-7` in that block,
and `MAX_COLOURED_PHASE` in `src/lib/phases.ts`. The admin form tells you so
when you invent the phase.
